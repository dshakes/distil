# 0015 — No per-command shell-output profiles (yet)

- **Status:** accepted (decision: do not build)
- **Date:** 2026-09-24
- **Relates to:** `benchmarks/results/2026-09-24/shell_headroom.py` and `shell_headroom.json`,
  `distil/adapters/anthropic.py` (`_compress_tool_result_text`), `distil/compress/recency.py`,
  ADR 0006, ADR 0008

## Context

RTK (`rtk-ai/rtk`) wraps common dev commands — `git status/log/diff`, `cargo`/`npm`/`pytest`
test runs, `ls`/`find`/`grep` — and rewrites their output with per-command rules, claiming
60–90% on those outputs. Distil has no per-command profiles; it digests every tool_result
with one generic, reversible pipeline (tier-1 + salience + keep policy). The question was
whether per-command profiles would add enough on top of that to be worth a new transform
surface.

Synthetic shell output has manufactured fake gaps in this repo before, so the gate was a
measurement on real traffic only: 3,585 local Claude Code transcripts (69,332 billed
requests, the provider's own `usage` per request, the original Bash command and output for
49,206 shell results), cross-checked against distil's content-free census
(14,332 proxied requests, all in `digest` mode). Every figure below is in
`benchmarks/results/2026-09-24/shell_headroom.json`, regenerated by the script beside it.

Bill model: input 1, cache write 1.25, cache read 0.1, output 5 (input-token equivalents).
A shell result is written to the cache once and read on every later request until the
next `/compact`, so removing a token at first sight is worth `1.25 + 0.1 × (later − 1)`.
Tool-result sizes are heuristic tokens; the bill is rescaled by the learned calibration
factor (1.2762 billed tokens per heuristic token at the snapshot) so both sides are on one
scale. Both inputs are live — transcripts grow and the factor keeps learning — so the
committed JSON is the snapshot this decision rests on; a re-run will differ in the last digit.

## What was measured

| | share of the bill |
|---|---|
| all tool results | 22.0% |
| Bash outputs | 15.8% |
| Bash outputs excluding whole-file reads (`cat`, `sed -n`, … stay byte-exact by the exact-quote rule) | 12.6% |
| what distil's digest already removes from those | 7.2% (61.5% of their tokens) |
| what is left after the digest | 5.4% |

**The digest is already the first-sight, cache-stable baseline.** Recency is anchored to
the client's `cache_control` breakpoint (`compress/recency.py`), and Claude Code pins its
newest message, so a shell output is digested the first time it is sent and never
rewritten. A profile would have to beat that, not the raw bytes.

**The volume is not where RTK's profiles are.** By bill weight the top eligible families
are `grep` (2.5%), `python3`/`python` (3.2% together), `sed` (1.3%), `echo`, `ls`, `awk`,
`for` loops, `gh pr`. `pytest` is 0.2%; `git show` and `git diff` are about 0.15% each;
`git status` and `git log` are not in the top fifteen. Most shell volume is ad-hoc scripts
whose output has no command-shaped structure a profile could know in advance.

**Incremental headroom**, crediting a profile with RTK's *best* claimed ratio (90%) on
every output it could apply to, net of what the digest already removes per result:

| scope | incremental share of the bill |
|---|---|
| RTK's own command families (`git *`, test runners, `ls`/`find`/`grep`/`rg`, package managers) | **1.4%** |
| every eligible shell output, including ad-hoc scripts no profile can cover | 4.2% |
| RTK families on a lossless-only session (nothing digests there) | 3.7% |

## Decision

Do not build per-command profiles. The realistic figure, 1.4%, is an upper bound — it
assumes RTK's best marketing ratio on every matching output — and it sits below the ~2%
of the bill that would justify a second transform surface with its own verdict-preservation
and recoverability tests. It is linear in the calibration factor and would reach 2% only at
a pooled factor of about 1.84, against 1.28 learned (the factor moved from 1.16 to 1.28
during this measurement, which is why that sensitivity is stated). The 4.2% row is not
reachable: it needs a profile for `python3 some_script.py`.

The lossless-only row is not reachable either. A profile that drops lines needs
`distil_expand` to stay recoverable, and lossless-only (the subscription default, and the
`PostToolUse` hook) never injects that tool — ADR 0006. Shipping it there would make the
transform silently lossy, which distil does not do.

## When to reopen

Re-run `uv run --python 3.12 python benchmarks/results/2026-09-24/shell_headroom.py` and
reopen if any of these hold:

- `rtk_families_90pct_net_of_digest` reaches 2% on real traffic — e.g. a user population
  whose agents run test suites and `git log` far more than this one does. The census cannot
  show that (it has no tool-name split), so the trigger is a contributed transcript
  measurement, not a guess.
- A recoverable path exists on lossless-only sessions (ADR 0006 changes), which would make
  the 3.7% row reachable.
- The digest's share of eligible shell tokens (61.5% here) drops — a regression there
  widens the gap a profile would fill, and should be fixed in the digest first.

## Consequences

- No new transform, no new store, no new flags. Shell output keeps going through the
  one generic, reversible, reject-if-bigger digest.
- The measurement script is kept so the decision can be re-checked in one command. It reads
  `~/.claude/projects` and `~/.distil` and writes only its own JSON: distil's restore store
  is pointed at a temp dir and its disk write is stubbed, so measuring never touches the
  user's recovery handles.
- The numbers are one maintainer's traffic. They are enough to refuse a build; they are not
  a public claim, so none of them appears on a gated page.
